# Security policy

## Reporting a vulnerability

Please **don't** open a public issue for security problems. Report them privately through [GitHub's security advisories](https://github.com/walriyami/Relay/security/advisories/new).

Include what you found, how to reproduce it, and what an attacker could do with it. Once a fix is available, the advisory will credit you unless you prefer anonymity. Only the latest release receives security fixes.

## Security model

Relay is built for a trusted group on a server you control. Public access to a shared link does not make the recipient a trusted member.

- **Initial setup requires proof only the owner has.** Until the administrator exists, setup asks for a random one-time key. Relay prints it in its server log at startup, and again at most every five minutes while someone has the setup page open, and keeps it in `<data>/setup.key` (readable only by its owner) until the administrator is created. On the Pi, read it with `walctl logs relay-production`; with Node directly, the default path is `.data/setup.key`. With Walriyami sign-in configured, Walriyami's administrator (as Walriyami Control reports it) can claim the server by signing in instead; nobody else can. The HTTP API never returns the key. `RELAY_SETUP_KEY=false` turns the key off, for a machine nobody else can reach; a leftover key file is then removed. It is ignored when `RELAY_ORIGIN` is a public web name rather than `localhost` or an IP address. Later accounts require invitations.
- **The public origin must be pinned.** Set `RELAY_ORIGIN=https://your-relay-host` and provide HTTPS at a trusted reverse proxy. Requests for other hostnames are rejected. Without an origin, only `localhost` and literal IP hosts work; arbitrary hostnames are rejected to prevent DNS rebinding. The public health probe is exempt and reveals no account or file data.
- **Cookies and request protection.** Sessions use `HttpOnly`, `SameSite=Lax` cookies, with the `__Host-` prefix and `Secure` flag over HTTPS. Unsafe requests reject mismatched origins and cross-site Fetch Metadata; authenticated state changes require a matching CSRF token. Passwords use scrypt, with bounded concurrent hashing; passkeys are also supported.
- **Wrong passwords cost the guesser, not the owner.** New passwords need at least 10 characters (older, shorter ones keep working). Each network (IPv4 /24 or IPv6 /48) gets 10 wrong passwords per account an hour, and each account gets 20 an hour from browsers it has never signed in on. A browser where the account has signed in before carries a signed `relay_known` cookie (it grants nothing by itself) and skips the account-wide limit, so guessing elsewhere can't lock the owner out of their own devices. Each network may run only two password checks at once, known browsers have their own room in the password queue, and a join with a dead invitation is refused before any password work. Passkeys skip all of this. Counts reset when Relay restarts.
- **Bearer URLs are credentials.** Anyone holding a link, request, invitation, or device sign-in URL can exercise its authority until it expires or is revoked. URLs derive from an HMAC key; the database stores token hashes. Shared file links can require a password (at least 8 characters), expire, or be limited to one recipient. Each network (IPv4 /24 or IPv6 /48) gets 10 wrong passwords per link every 15 minutes, so a stranger guessing can't lock out the person the link was meant for, and a link takes at most 100 wrong passwords an hour from everyone together; a browser that has already unlocked the link isn't asked again. Avoid posting private URLs in public places. Relay's own request log records route patterns rather than bearer URLs; configure your proxy logs likewise.
- **Numeric codes trade security for convenience.** A six-digit code can reveal a bearer URL, including a device sign-in link, so each code works for only a day after it's issued; the owner's screen shows a fresh one whenever they look, and the link and QR code never change. Each network (an IPv4 address or IPv6 /64) gets 5 wrong codes per 15 minutes and 20 per day. When Relay sees 30 wrong codes within an hour from anywhere, it tells the administrator (in the log and in Admin) and, for six hours after the guessing stops, each wider network (IPv4 /24 or IPv6 /48) gets only 3 wrong codes a day. Code entry never pauses for everyone: a right code from a network that hasn't been guessing always works. These limits make guessing slow, not impossible, and the counts reset when Relay restarts. A code's digits stay reserved for 30 days after it ends, so a remembered code never opens someone else's share. Use a password on sensitive file shares, revoke unused links, and prefer bearer URLs or QR codes for sensitive handoffs.
- **Walriyami sign-in follows Walriyami Control.** With the `WAL_*` settings, Relay asks Control whether each person signed in with Walriyami may still use it, every 10 seconds while they do, and ends their sessions when Control says no, including those of browsers they added with a sign-in code from a Walriyami session. An outage is not a no: sessions Control confirmed within the last hour keep working, and after that requests wait for Control rather than signing anyone out. So someone whose access is removed while Control is unreachable can keep using Relay for up to an hour. Relay remembers confirmations in memory, so a restart during an outage starts that hour again.
- **Proxy trust is explicit.** Relay takes a client's address from `X-Forwarded-For` only on connections from a proxy listed in `RELAY_TRUST_PROXY`, which defaults to loopback. List only proxies that you control and that replace forwarding headers, by address, range, or container name on a shared Docker network. A name is trusted at the addresses it resolves to at the time, so no other container on that network can claim to be the proxy. Do not trust every private-network address or blindly accept Internet-supplied forwarding headers. Relay logs once when an unlisted address sends forwarding headers. When a trusted proxy names the visitor in a header of its own, such as Cloudflare's `CF-Connecting-IP`, set `RELAY_CLIENT_IP_HEADER` to it; Relay reads it only on connections from a trusted proxy and only when it holds an address; when it is missing or isn't an address, the request counts as the proxy's own, never as an `X-Forwarded-For` the visitor may have sent. `X-Forwarded-Host` is ignored: the host is the `Host` header the proxy routed by. A trust entry of `0.0.0.0/0` or `::/0` stops startup. Only Cloudflare should be able to reach that proxy. Without a verified client-address chain, proxied users share one rate-limit bucket. See [Hosting](docs/hosting.md#settings).
- **Nearby connects devices directly.** Relay authorizes every Nearby signal: a member's own devices, other members' devices only when both members are visible and at the same network address, and guests only with the member whose unexpired code they used. Once connected, files and text travel over encrypted WebRTC data channels between the two browsers and never reach the server. There are no STUN or TURN servers, so the browsers only try each other's local addresses; each browser shares its local addresses, or `.local` names that stand for them, with the other side. Only a member's own devices accept automatically. Other members and guests are asked first, and each member can hide their devices from other members. A Nearby code is a bearer credential like the others: anyone holding it can join under any name and offer files until the code ends. Received files are not scanned by Relay.
- **Names other people see are plain text.** Display names, device names, request names and senders, invitation notes and Nearby guest names are kept to one line, and link notes and request messages keep only their line breaks. Control characters and the invisible characters that change text direction are removed, so a name can't span several lines to pose as a notice from Relay or show its letters in a different order. Names saved before this rule keep whatever they held; the web app shows them as text, never as markup.
- **Notifications go only to known push services, and only encrypted.** Each device opts in. Relay sends to a subscription only if its address belongs to Google's, Mozilla's, Apple's or Microsoft's push service over HTTPS, so a member can't make the server call other addresses. Messages are encrypted for that browser (RFC 8291) and signed with a key pair Relay generates on first use and keeps in `push-keys.json` in the data storage, readable only by its owner. They carry a short title and description such as a device or file name; the push service can see when and how often a device is notified, but not what a message says. A device's subscription is deleted when it signs out or its session ends, and when the push service reports it gone. Another account can take over a browser's subscription only from that browser, which holds the subscription's keys; knowing its address isn't enough.
- **The installed app keeps no private data offline.** Relay's service worker (`public/sw.js`) caches only the app's own files: never `/api/`, `/uploads/`, `/local/` or any file content. Something shared to Relay from another app is held in that browser's storage until Relay puts it in the Send draft, and is cleared on sign-out; the server's `/share` address only discards what reaches it.
- **Members' data is isolated through the API.** The administrator dashboard does not browse members' files, links, or activity; when stored files are damaged it shows whose and how many, not which. Administrators are nevertheless fully trusted: they can reset a member's password and impersonate that member, make other members administrators, and permanently remove any member except themselves, deleting that member's files and links. Every administrator is equal, including over other administrators; Relay only refuses to leave none. **Admin → History** keeps 90 days of account events, failed sign-ins, and when each member sent or shared something, with sizes and counts but never file names, link addresses, contents or network addresses; a failed sign-in for a username that doesn't exist isn't written down by name. A removed member who signs in through single sign-on and still has access there comes back as a new, empty account. Anyone with host, volume, database, backup, or secret-key access is also trusted.
- **Administrator recovery belongs to the server's owner.** With `RELAY_RECOVER_ADMIN=<username>` set, Relay writes a one-time link to its log at startup. The link sets that administrator's password, signs the account out everywhere and removes its passkeys. It works once, for 24 hours, and only for an existing administrator; the database keeps only its hash, and its checks are rate limited like sign-ins. Anyone who can read the log while the setting is on can take over that account, so keep logs private and clear the setting afterwards.
- **Resource limits reduce abuse.** Upload limits, download authorization, archive entry/text limits, decoder limits, and bounded hashing protect common resource-exhaustion paths. Previews decode only PNG, JPEG, GIF, WebP and HEIF/AVIF, recognised by the file's own bytes rather than its name or type, in a separate worker with every other image decoder switched off. An upload holds room for its declared size only while it makes progress: one from a request link that receives less than 4 MB in 30 minutes is given up, and a member's own after a day, so declaring a large upload and sending nothing (or a byte now and then) can't keep a request full. Room that request-link visitors have declared but not yet sent never stops a member from uploading; it counts only against other visitors. In production, walctl runs the container as non-root with no Linux capabilities, `no-new-privileges` and a memory limit. Its root filesystem is writable and there is no process-count limit. These controls do not eliminate denial of service.

Relay is **not end-to-end encrypted**. The host can read stored files. Restrict host and backup access, use disk encryption appropriate to your data, keep dependencies and the host patched, and avoid running unrelated untrusted workloads on the same Docker network. Thumbnail worker threads provide scheduling and memory limits, **not an operating-system sandbox** against a native decoder vulnerability.

A source audit does not certify a live deployment, tunnel configuration, host, or all future changes. The
[historical audit record](docs/archive/2026-09-30/security-audit.md) describes its recorded candidate, scope, fixes,
validation, and limitations. Its findings and test results must be reassessed for the current checkout.
