# Security policy

## Reporting a vulnerability

Please **don't** open a public issue for security problems. Report them privately through [GitHub's security advisories](https://github.com/walriyami/Relay/security/advisories/new).

Include what you found, how to reproduce it, and what an attacker could do with it. Once a fix is available, the advisory will credit you unless you prefer anonymity. Only the latest release receives security fixes.

## Security model

Relay is built for a trusted group on a server you control. Public access to a shared link does not make the recipient a trusted member.

- **Initial setup requires proof only the owner has.** Until the administrator exists, setup asks for a random one-time key. Relay prints it in its server log at startup, and again at most every five minutes while someone has the setup page open, and keeps it in `<data>/setup.key` (readable only by its owner) until the administrator is created. On the Pi, read it with `walctl logs relay-production`; with Node directly, the default path is `.data/setup.key`. With Walriyami sign-in configured, Walriyami's administrator (as Walriyami Control reports it) can claim the server by signing in instead; nobody else can. The HTTP API never returns the key. `RELAY_SETUP_KEY=false` turns the key off, for a machine nobody else can reach; a leftover key file is then removed. It is ignored when `RELAY_ORIGIN` is a public web name rather than `localhost` or an IP address. Later accounts require invitations.
- **The public origin must be pinned.** Set `RELAY_ORIGIN=https://your-relay-host` and provide HTTPS at a trusted reverse proxy. Requests for other hostnames are rejected. Without an origin, only `localhost` and literal IP hosts work; arbitrary hostnames are rejected to prevent DNS rebinding. The public health probe is exempt and reveals no account or file data; it names the build only by its short commit.
- **Cookies and request protection.** Sessions use `HttpOnly`, `SameSite=Lax` cookies, with the `__Host-` prefix and `Secure` flag over HTTPS. Unsafe requests reject mismatched origins and cross-site Fetch Metadata; authenticated state changes require a matching CSRF token. Passwords use scrypt, with bounded concurrent hashing; passkeys are also supported.
- **Wrong passwords cost the guesser, not the owner.** New passwords need at least 10 characters (older, shorter ones keep working). Each network (IPv4 /24 or IPv6 /48) gets 10 wrong passwords per account an hour, and each account gets 20 an hour from browsers it has never signed in on. A browser where the account has signed in before carries a signed `relay_known` cookie (it grants nothing by itself) and skips the account-wide limit, so guessing elsewhere can't lock the owner out of their own devices. So does a new browser on a network the account has signed in from before with its current password (home, work; up to 20 networks, for 400 days): a stranger elsewhere can't borrow that network, and it keeps its own limit of 10 an hour. Where a network is shared with strangers (a mobile carrier's address pool, a VPN exit, hotel Wi-Fi), they skip the account-wide limit too, and while an account is held back someone there can tell from the different answer that its owner has signed in from that network. A right password alone never gets past the limit, since that would let a guesser test passwords against it. Each network may run only two password checks at once. The password queue keeps room for known browsers, and then for networks that haven't been getting passwords wrong (joins and first sign-ins), so a flood of guesses waits behind everyone else and is turned away first; a network's second check at once also waits behind. This holds against guessing from a few networks; someone with very many networks gets each one's first few checks in the shared room. A join with a dead invitation is refused before any password work. Passkeys skip all of this. Wrong passwords are counted in the database, so a restart forgives nobody. A passkey request holds a challenge in memory for five minutes; each wider network may hold at most 1,000, and a full store makes room from the network holding the most, so a flood from one network can't push out anyone else's.
- **Bearer URLs are credentials.** Anyone holding a link, request, invitation, or device sign-in URL can exercise its authority until it expires or is revoked. Taking access away also stops downloads already running: every download, ZIP and **Download all my files** asks again whether it may go on as it runs (right after its first bytes, then after each megabyte and at least once a second, each time a lookup of one row), so turning a link off, signing a device out, suspending a member or deleting an item forever cuts them short, and the download fails rather than finishing. URLs derive from an HMAC key; the database stores token hashes. Shared file links can require a password (at least 8 characters), expire, or be limited to one recipient. Each network (IPv4 /24 or IPv6 /48) gets 10 wrong passwords per link every 15 minutes, so a stranger guessing can't lock out the person the link was meant for, and a link takes at most 100 wrong passwords an hour from everyone together; a browser that has already unlocked the link isn't asked again. These counts survive a restart. Avoid posting private URLs in public places. Relay's own request log records route patterns rather than bearer URLs; configure your proxy logs likewise.
- **Numeric codes trade security for convenience.** A six-digit code can reveal a bearer URL, including a device sign-in link, so each code works for only a day after it's issued; the owner's screen shows a fresh one whenever they look, and the link and QR code never change. Each address (an IPv4 address or IPv6 /64) gets 5 wrong codes per 15 minutes and 20 per day, and its network (an IPv4 /24 or IPv6 /56) 50 per day in all, so many addresses in one network can't add up to more. When Relay sees 30 wrong codes within an hour, or 50 within a day, from anywhere, it tells the administrator (in the log and in Admin) and, for six hours after the guessing stops, each network gets only 3 wrong codes a day and each IPv6 /48 only 10. However many networks someone uses, all of them together get 300 wrong codes a day: once that is spent, codes are paused for anyone who isn't signed in until the oldest of them is a day old, and the log says so. Someone guessing can therefore pause code entry for visitors, including signing in a new device with its code, but not links, QR codes (a device's sign-in link included), passwords or passkeys, which keep working; signed-in members can still enter codes. A code that has ended answers exactly like one that never existed. A share's code is issued only when its owner looks at that share, not whenever the list of links loads. These limits make guessing slow, not impossible; the counts are kept in the database, so a restart forgives nobody. A code's digits stay reserved for 30 days after it ends, so a remembered code never opens someone else's share. Because of that, each member's shares, requests, invitations and Nearby codes get at most 500 new codes a day, counting the daily renewal of open ones (device sign-in codes have their own 100), so one member can't use up the six-digit space quickly; once that is spent, new ones are refused until tomorrow and open ones show no code, while their links and QR codes keep working. A new code tries at most 64 candidates rather than holding up the server: creating something then answers 503, and an open one shows no code. If the secret key changes, owners are shown fresh codes for their open shares, requests, invitations and Nearby codes; the old ones stop working, and their digits are no longer held back for a month. Use a password on sensitive file shares, revoke unused links, and prefer bearer URLs or QR codes for sensitive handoffs.
- **Walriyami sign-in follows Walriyami Control.** With the `WAL_*` settings, Relay asks Control whether each person signed in with Walriyami may still use it, every 10 seconds while they do, and ends their sessions when Control says no, including those of browsers they added with a sign-in code from a Walriyami session. An outage is not a no: sessions Control confirmed within the last hour keep working, and after that requests wait for Control rather than signing anyone out. So someone whose access is removed while Control is unreachable can keep using Relay for up to an hour. Relay remembers confirmations in memory, so a restart during an outage starts that hour again.
- **Proxy trust is explicit.** Relay takes a client's address from `X-Forwarded-For` only on connections from a proxy listed in `RELAY_TRUST_PROXY`, which defaults to loopback. List only proxies that you control and that replace forwarding headers, by address, range, or container name on a shared Docker network. A name is trusted at the addresses it resolves to at the time, so no other container on that network can claim to be the proxy. Do not trust every private-network address or blindly accept Internet-supplied forwarding headers. Relay logs once when an unlisted address sends forwarding headers. While a proxy listed by name doesn't resolve (its container hasn't started, or is being recreated), requests that carry the client-address header from an address Relay doesn't trust get 503 "Relay is starting up" rather than all counting as one visitor, whose wrong passwords would lock out everyone; a mistyped name therefore turns away everything sent through the proxy, and the log says which name doesn't resolve. A resolver that briefly fails keeps the addresses a name had, and a request from an address Relay doesn't trust has the names looked up again first, so a proxy that moves is followed at once. When a trusted proxy names the visitor in a header of its own, such as Cloudflare's `CF-Connecting-IP`, set `RELAY_CLIENT_IP_HEADER` to it; Relay reads it only on connections from a trusted proxy and only when it holds an address; when it is missing or isn't an address, the request counts as the proxy's own, never as an `X-Forwarded-For` the visitor may have sent. `X-Forwarded-Host` is ignored: the host is the `Host` header the proxy routed by. A trust entry of `0.0.0.0/0` or `::/0` stops startup. Only Cloudflare should be able to reach that proxy. Without a verified client-address chain, proxied users share one rate-limit bucket. See [Hosting](docs/hosting.md#settings).
- **Nearby connects devices directly.** Relay authorizes every Nearby signal: a member's own devices, other members' devices only when both members are visible and at the same network address, and guests only with the member whose unexpired code they used. Once connected, files and text travel over encrypted WebRTC data channels between the two browsers and never reach the server. There are no STUN or TURN servers, so the browsers only try each other's local addresses; each browser shares its local addresses, or `.local` names that stand for them, with the other side. Relay passes on only UDP candidates with a private, link-local or `.local` address, and each browser ignores any other it's given, loopback included, so a guest can't learn a member's public address, make a member's browser contact the internet, or aim it at a port on the member's own machine. A guest can still name another address on the member's local network, which the browser then sends connection checks to. Each sender may send a device about 20 signals at once and one more every two seconds, and a device whose stream has fallen behind gets none until it catches up (the sender tries again); a stream that stops reading is closed rather than held in memory. Only a member's own devices accept automatically. Other members and guests are asked first, and each member can hide their devices from other members. A Nearby code is a bearer credential like the others: anyone holding it can join under any name and offer files until the code ends. Received files are not scanned by Relay.
- **Names other people see are plain text.** Display names, device names, request names and senders, invitation notes and Nearby guest names are kept to one line, and link notes and request messages keep only their line breaks. Control characters become spaces (or go, in a message), and the invisible characters that can reorder text are removed, so a name can't span several lines to pose as a notice from Relay or show its letters in a different order. Names saved before this rule are not rewritten; the web app shows them as text, never as markup, leaves out any direction override they hold, and sets every name, note and file name apart from the words around it (`<bdi>`), so right-to-left letters can't reorder a sentence such as "From Sara · 3 files". Push notifications leave out the same overrides.
- **File and folder names show what they are.** Besides what file systems refuse, a file, folder or item name may not hold direction marks, invisible spaces and blank-looking fillers (zero-width spaces, word joiners, Hangul fillers, the blank braille pattern and similar), or more than three spaces in a row, nor be blank, so a name can't push its real ending out of sight ("invoice.pdf" followed by many spaces and ".exe"). This applies to uploads and their folders, renames, text items and what visitors send to a request link; the web app cleans names that come from a disk or over Nearby the same way instead of refusing them, and an item made from a request and a sender's name is named without them. Names stored before this rule still list, download, delete and take more files; downloads, and the entries inside a ZIP, carry the cleaned name instead, with a number added when that matches another name in the same folder. Letters that merely look alike (Cyrillic "а" for Latin "a") are not refused; the type label on a file's picture ("EXE") comes from its real ending.
- **Notifications go only to known push services, and only encrypted.** Each device opts in. Relay sends to a subscription only if its address belongs to Google's, Mozilla's, Apple's or Microsoft's push service over HTTPS, so a member can't make the server call other addresses. Messages are encrypted for that browser (RFC 8291) and signed with a key pair Relay generates on first use and keeps in `push-keys.json` in the data storage, readable only by its owner. They carry a short title and description such as a device or file name; the push service can see when and how often a device is notified, but not what a message says. A device's subscription is deleted when it signs out or its session ends, and when the push service reports it gone. Another account can take over a browser's subscription only from that browser, which holds the subscription's keys; knowing its address isn't enough.
- **The installed app keeps no private data offline.** Relay's service worker (`public/sw.js`) caches only the app's own files: never `/api/`, `/uploads/`, `/local/` or any file content. Something shared to Relay from another app is held in that browser's storage until the member adds it to the Send draft or discards it. At most five shares wait at once: a new one replaces the oldest, so a website posting the form over and over can't fill the browser's storage. Anything left for more than a day is dropped the next time Relay opens or something is shared, and everything is cleared on sign-out. Relay shows what arrived and asks before adding it, because a website can post the same share form or open the same `/share#text=…` address; the server's `/share` address only discards what reaches it.
- **Members' data is isolated through the API.** The administrator dashboard does not browse members' files, links, or activity; when stored files are damaged it shows whose and how many, not which. Administrators are nevertheless fully trusted: they can reset a member's password and impersonate that member, make other members administrators, and permanently remove any member except themselves, deleting that member's files and links. Every administrator is equal, including over other administrators; Relay only refuses to leave none. **Admin → History** keeps 90 days of account events, failed sign-ins, and when each member sent or shared something, with sizes and counts but never file names, link addresses, contents or network addresses; a failed sign-in for a username that doesn't exist isn't written down by name. A removed member who signs in through single sign-on and still has access there comes back as a new, empty account. Anyone with host, volume, database, backup, or secret-key access is also trusted.
- **Administrator recovery belongs to the server's owner.** With `RELAY_RECOVER_ADMIN=<username>` set, Relay writes a one-time link to its log at startup. The link sets that administrator's password, signs the account out everywhere and removes its passkeys. It works once, for 24 hours, and only for an existing administrator; the database keeps only its hash, and its checks are rate limited like sign-ins. Anyone who can read the log while the setting is on can take over that account, so keep logs private and clear the setting afterwards.
- **Resource limits reduce abuse.** Relay checks who is asking before it reads a request's body: a stranger is refused before any of it is parsed. It checks again, from the database, once the body has arrived, so a request whose sender was signed out, suspended or demoted while it was still arriving is refused as any new request would be and changes nothing; an administrator's removal of a member also stops part way, leaving the member suspended, if that administrator is signed out or demoted meanwhile. Only members and a request link's own visitors may send the larger upload descriptions (up to 32 MiB); everything else stops at 1 MiB. Visitors, who need only a request link, may have at most four of those over 1 MiB read at once, and no more than two of them from one request link or one network; the rest are asked to try again shortly. Of the guest cookies a browser sends, only well-formed ones count, at most 32, in a single lookup each time they are checked. Upload limits, download authorization, archive entry/text limits, a limit of 64 nested levels in an uploaded path (so no upload can make itself impossible to delete), decoder limits, and bounded hashing protect common resource-exhaustion paths. Previews decode only PNG, JPEG, GIF, WebP and HEIF/AVIF, recognised by the file's own bytes rather than its name or type, in a separate worker with every other image decoder switched off. An upload holds room for its declared size only while it makes progress: a send from a request link that hasn't received 4 MB (or, if smaller, begun) within 10 minutes (unless the same visitor is busy sending something else), or that then receives less than 4 MB in 30 minutes, is given up, and a member's own after a day, so declaring a large upload and sending nothing (or a byte now and then) can't keep a request full for long. Room that request-link visitors have declared but not yet sent never stops a member from uploading; it counts only against other visitors. A visitor's bytes are checked against the server's capacity again as they arrive, so uploads that overlap can't together go past it. These checks, and the room a request's page shows, read running totals the database keeps as uploads start, progress and end, so their cost doesn't grow with the number of unfinished files on the server or in the request. A request-link visitor's send lists at most 5,000 files and folders (refused before the list is worked through), its text at most 200,000 bytes, a request holds at most 20,000 entries, and one network (an IPv4 /24 or IPv6 /56) may keep at most 10 sends to a request open, however many visits it starts, and at most 64 visits to it, 16 from one address: starting another forgets one with no send open, that address's own oldest first; it may hold 8 live-update streams to a request's pages, a request 30 in all and all request visitors on the server 300, after which pages ask for updates every so often instead. Every send counts towards an hourly allowance, even one cancelled straight away: one network may start 60 sends to a request listing 20,000 files and folders in all (counting the folders a file's path implies), and a request takes 300 sends and 100,000 entries from everyone; past that, visitors are told to try again later, while sends already started carry on. Starting or cancelling a send of thousands of files adds up the running totals in a few statements rather than file by file, so it never holds other requests up for long. A visit keeps on record at most 16 of its pages that sent nothing; naming another forgets the one used or closed longest ago. Turning a stream away costs no database work per open stream and, for a visitor, leaves no record behind. A shared link records a browser for its owner only when it comes back with the visitor cookie Relay just set (a browser does that by itself), so a script that keeps no cookies records nothing and uses up no visitor limit. One network (an IPv4 /24 or IPv6 /48) adds at most 30 new people an hour to a link without a limit or password; past that the link still opens for them, uncounted. A link without a limit keeps its 1,000 most recently active visits (on a password link, someone whose visit was forgotten is asked for the password again), while its counts keep everyone, and listing links reads those counts rather than the visits. People opening or downloading from one link within an hour of each other share one Activity entry, and the feed always shows the 30 newest sign-ins and password and passkey changes, so a link's visitors can't push them out. Preparing a ZIP checks each file in it on disk first, so only a few are prepared at once: two for one member (their items' and folders' ZIPs and **Download all my files** together), two for everyone downloading from one member's links, two for everyone downloading from anyone's links (so members always keep two of the server's places), and four on the server; more are asked to try again shortly, and browsing never waits for them. A ZIP being prepared already is waited for rather than prepared again, and **Download all my files** keeps what it worked out for a minute from when its checks finish, so the HEAD a browser sends first doesn't check every file twice. In production, walctl runs the container as non-root with no Linux capabilities, `no-new-privileges` and a memory limit. Its root filesystem is writable and there is no process-count limit. These controls do not eliminate denial of service.

Relay is **not end-to-end encrypted**. The host can read stored files. Restrict host and backup access, use disk encryption appropriate to your data, keep dependencies and the host patched, and avoid running unrelated untrusted workloads on the same Docker network. Thumbnail worker threads provide scheduling and memory limits, **not an operating-system sandbox** against a native decoder vulnerability.

A source audit does not certify a live deployment, tunnel configuration, host, or all future changes. The
[historical audit record](docs/archive/2026-09-30/security-audit.md) describes its recorded candidate, scope, fixes,
validation, and limitations. Its findings and test results must be reassessed for the current checkout.
