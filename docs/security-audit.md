# Relay security audit — 27 September 2026

This audit reviewed the local Relay source, dependency lockfile, Git history available in this checkout, browser access flows, and container configuration. Fixes are in this working tree; they have not been pushed or deployed. The starting revision was `4b4b5b8` with existing interface and gateway changes preserved.

## Numeric-code protection policy

Four digits provide 10,000 values, including `0000`. With 100 active four-digit codes, one uniformly random guess has a 1% chance of finding an active code; the destination may impose further access checks. Lockouts cannot make that initial probability zero.

The preferred length remains under administrator control. Five incorrect codes from one address within 60 seconds trigger a one-minute address lockout. Ten incorrect codes across all addresses within 60 seconds trigger a two-minute service-wide pause. Repeat lockouts double, up to one hour; IPv6 addresses are grouped by /64. The public pickup endpoint and direct numeric sign-in endpoint share this budget.

Either an address lockout or a service-wide pause temporarily replaces four-digit codes with fresh six-digit codes. Recovery requires 15 minutes without further rejected guessing; blocked attempts extend that period. Strike history resets after 24 hours of quiet. Protection survives server restarts, stores HMAC-derived address identifiers, and exposes the current pause and code-length override to users and administrators. Ordinary typos below the thresholds do not create an attack notice.

Retired codes are never reused. If fresh four-digit assignments are unavailable, six-digit mode remains active and the interface explains why. If stronger numeric assignments cannot be allocated, numeric entry fails closed while existing bearer URLs remain valid. This avoids repeatedly scanning an exhausted namespace on public requests. Changing or rotating a numeric code does not revoke a bearer URL that somebody already learned.

## Verification

- `npm run check`: passed formatting, TypeScript, ESLint, and **181/181 backend tests**.
- `npm run build`: passed. The production image also built successfully during container verification.
- `npm run verify:container`: passed using disposable containers and volumes. A competing writer was refused; a 96 MiB upload survived a forced process kill and resumed with matching content; full-disk admission and writes returned 507 without advancing the upload offset, then recovered.
- Compose configuration: default and custom network/proxy settings rendered successfully. Caddy configuration validated, and a disposable proxy-to-echo test confirmed that untrusted forwarding headers were discarded while trusted multi-hop chains resolved right to left to a single client IP.
- Cross-browser verification: **789 passed, 23 skipped** across Chromium, Firefox, WebKit, and mobile projects (812 cases). Results combine the initial run, a focused setup rerun, and the remaining cases. The initial failures came from a setup-test helper checking focus after filling the new key field; correcting the assertion order resolved them.

Regressions cover setup-key lifecycle, hostname/origin boundaries, concurrent password guesses, password-change revocation, bounded hashing, title validation, archive bounds, shared numeric-failure budgets, escalating/restarted lockouts, exhausted code namespaces, and bearer-link continuity. Browser coverage includes visible protection notices and a real bearer-link fallback when no numeric assignment is available.

The dependency audit reported **zero known advisories** at the time of the audit. A pattern scan of **1,781 historical blobs across five locally available commits** found no common private-key, GitHub, AWS, OpenAI, or Slack credential signatures. Pattern scans cannot prove that arbitrary, revoked, unrecognized, or unavailable-history secrets were never published.

## Deployment requirements and remaining limits

1. Deploy the corrected version explicitly; this audit does not change the running service. Review `.env.example` and [self-hosting](self-hosting.md) before updating.
2. Pin the exact public HTTPS origin. On a host others can reach before setup is finished, set `RELAY_SETUP_KEY=true` so the first administrator needs the local setup key; already initialized installations do not repeat setup.
3. Configure the real tunnel/proxy chain explicitly. The default no longer trusts the entire Docker private range. Compose trusts its dedicated gateway address; the gateway accepts client addresses only from explicitly trusted upstream proxies. Until that upstream chain is correctly configured, visitors behind a tunnel conservatively share a rate-limit bucket. No live proxy/tunnel settings were inspected or changed.
4. Short numeric codes can still be guessed before protection triggers, and a successful guess can reveal a durable bearer URL or sign-in handoff. Lockouts cannot retract a URL already learned. Review/revoke sensitive shares and use passwords where appropriate. The global pause is also an intentional availability tradeoff: an attacker can interrupt numeric-code entry while bearer links remain available.
5. Administrators are trusted and can impersonate members through password resets. Server/volume/backup access can read file contents. Relay is not end-to-end encrypted.
6. Thumbnail decoders run in worker threads with bounds, not an OS sandbox. Container controls limit some consequences but do not guarantee protection against native-code or kernel vulnerabilities. Denial of service remains possible within configured resource budgets.
7. This was a source-and-isolated-test audit with implementation-context review, not an independent penetration test or an audit of the live host, external services, all published releases, or future changes.
